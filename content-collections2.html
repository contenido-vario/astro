Content Collections Astro 7.1+ (2026/07)

Las Content Collections (Colecciones de Contenido) son una característica nativa que ya viene integrada en el núcleo de Astro (desde la versión 2.0).

Lo único que debemos hacer para empezar a usar las Colecciones de Contenido es estructurar las carpetas de una forma específica y crear un archivo de configuración.

Paso 1: Crear un archivo llamado content.config.ts en la raiz del proyecto

A partir de la versión 7.1 de Astro, el archivo de configuración pasa a llamarse content.config.ts y debe estar ubicado directamente en la raíz del proyecto (fuera de src), y cada colección requiere obligatoriamente un loader (como glob) para indicarle a Astro dónde buscar esos archivos.

El cambio principal que hicieron (conocido como la Content Layer o capa de contenido) se debió a una razón muy clara: querían que Astro no dependiera únicamente de los archivos Markdown guardados en el ordenador, sino que pudiera traer contenido desde cualquier sitio de forma unificada.

Antes, el sistema de colecciones estaba limitado a leer los archivos de texto que tenías dentro de la carpeta src/content.

La idea detrás del cambio es darle mucha más potencia al framework para conectar con cualquier fuente de datos moderna. Con este nuevo cambio, el equipo de Astro busca:

  1. Flexibilidad: Permitir que los datos de una colección no solo vengan de archivos locales, sino también de bases de datos externas, un CMS en la nube (como Notion o Strapi) o una API de internet, usando siempre las mismas herramientas y validaciones.
  2. Mejor rendimiento y escalabilidad: Manejar mejor los proyectos grandes donde hay miles de artículos o páginas, guardando la información de manera más eficiente al compilar la web.

Cambios:

El loader es el nuevo puente entre los archivos físicos y el sistema de colecciones de Astro:

  1. Los archivos .md, .mdx deben estar guardados en una carpeta dentro de ./src/content/ ejemplo: ./src/content/posts.
  2. La función glob: Actúa como un rastreador que entra en esa carpeta, encuentra todos los archivos .md/.mdx y se los entrega a Astro.
  3. El esquema zod (schema): Una vez que el glob encuentra los archivos, el esquema comprueba que todos tengan su título, fecha y datos correctos.

Paso 2: Contenido del nuevo archivo content.config.ts


import { defineCollection} from 'astro:content';
import { glob } from 'astro/loaders';
import { z } from 'astro/zod'; // <-- CAMBIO 

const posts = defineCollection({
  loader: glob({ 
    pattern: '**/*.{md,mdx}', 
    base: './src/content/posts' 
  }),
  schema: ({ image }) => z.object({
    title: z.string(),
    pubDate: z.coerce.date(),
    description: z.string(),
    author: z.string(),
//  Para indicar una imagen
    image: z.object({
      url: image(), // <--- Astro valida que el archivo exista de verdad
      alt: z.string(),
    }),
    tags: z.array(z.string()),
    cover: image().optional(),
  }),
});

export const collections = { posts };

Imaginemos ahora que tenemos dos colecciones: una colección de posts para un blog y otra de productos para una tienda. ¿Cómo quedaría el content.config.ts con el cambio?

  1. Cada colección su loader: Cada una apunta a su propia carpeta dentro de src/content/ (por ejemplo, src/content/posts/ y src/content/productos/).
  2. El objeto collections define el nombre de la colección: Las claves que se ponen ahí (posts y productos) son las que luego se usarán en el código para llamar a cada colección (por ejemplo: getCollection('posts') o getCollection('productos')).

import { defineCollection } from 'astro:content';
import { glob } from 'astro/loaders';
import { z } from 'astro/zod';

// 1. Definir la colección de posts
  const postsCollection = defineCollection({
  loader: glob({ 
    pattern: '**/*.{md,mdx}', 
    base: './src/content/posts' 
  }),
  schema: ({ image }) => z.object({
    title: z.string(),
    pubDate: z.coerce.date(),
    description: z.string(),
    author: z.string(),
    image: z.object({
      url: image(),
      alt: z.string(),
    }),
    tags: z.array(z.string()),
  }),
});

// 2. Definir la colección de productos 
// (si se usan archivos JSON/YAML para productos,
//  se puede cambiar el patrón a '**/*.json')
const productosCollection = defineCollection({
  loader: glob({ 
    pattern: '**/*.{md,mdx}', 
    base: './src/content/productos' 
  }),
  schema: ({ image }) => z.object({
    name: z.string(),
    price: z.number(),
    stock: z.number(),
    category: z.enum(['comida', 'juguetes', 'accesorios']),
    isFeatured: z.boolean().default(false),
    productImage: image(),
  }),
});

// 3. Exportar todas las colecciones juntas
export const collections = {
  posts: postsCollection,
  productos: productosCollection,
};

Tipos de Colecciones

En la versión actual (Astro 7.1+), el manejo de archivos Markdown, MDX o JSON se hace directamente configurando el loader de glob adecuado para cada tipo de extensión de archivo, sin necesidad de declarar un type.

  1. Archivos de contenido: Archivos Markdown (.md) y MDX (.mdx).
  2. Archivos de datos estructurados: Archivos JSON (.json) y YAML (.yaml).

Si tienes código HTML que necesitas reutilizar o meter dentro de tus colecciones, usa archivos MDX.

Si el contenido tiene que estar sí o sí dentro de una Content Collection para beneficiarse de la validación de Zod y la facilidad de usar getCollection y ya se tiene hecho en .html o el diseño requiere algo más de lo que ofrece MarkDown, la extensión .mdx es la mejor aliada

Al cambiar la extensión de los archivos de .html a .mdx, se puedes escribir HTML puro y duro dentro de ellos, en vez de sólo Markdown. MDX es una extensión que permite mezclar Markdown, componentes de Astro y HTML estándar en un mismo archivo.

Para que Astro entienda los archivos .mdx en un proyecto, se necesita añadir la integración oficial


pnpm astro add mdx

Lo único que cambia en esta versión es dónde y cómo se configura (en el archivo content.config.ts de la raíz), pero la estructura interna de los artículos o productos por dentro sigue funcionando igual que antes.
